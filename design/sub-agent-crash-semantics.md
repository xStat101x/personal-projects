# Sub-Agent Crash & Partial-State Semantics (DRAFT v0.4)

When a sub-agent dispatched by the orchestrator (`recon-agent`, `enum-agent`, `vuln-agent`, `exploit-agent`, `report-agent`, `retro-agent`) finishes its work, it returns a structured result to the orchestrator. When it *doesn't* finish — context overflow, tool error, OS kill, model timeout, hung subprocess — the orchestrator needs to know which artifacts on disk are usable and which to discard.

This doc specifies the file-based handshake every sub-agent dispatch follows.

---

## 1. The three flag files

Every sub-agent dispatch writes to a phase-scoped subdirectory:

```
engagements/<id>/<phase>/.dispatch/<dispatch-id>/
    ├── task.json          # input spec the orchestrator handed in
    ├── heartbeat           # touched periodically while the agent is alive
    ├── .running            # written at dispatch start (presence = "currently running")
    ├── .done               # written on clean exit (replaces .running)
    └── .crashed            # written by reaper if .running is stale (replaces .running)
```

`<dispatch-id>` is a ULID generated by the orchestrator at dispatch time. It also appears in the audit log so dispatches are correlatable.

`<phase>` is one of `recon`, `enum`, `triage`, `verification`, `reporting`, `retro`.

Only **one** of `.running` / `.done` / `.crashed` exists at any given time per dispatch.

---

## 2. The lifecycle

### 2.1 Dispatch

The orchestrator:

1. Creates the dispatch directory.
2. Writes `task.json` (frozen — never modified after this point).
3. Writes `.running` containing a JSON object with `started_at`, `dispatched_by`, `expected_max_duration_seconds`.
4. Spawns the sub-agent (Claude Code `Agent` tool primary; filesystem-coordinated dispatch fallback per `PLAN.md §15`).
5. Updates `state.json` to reflect "phase X dispatched, awaiting result."

### 2.2 Heartbeat (while running)

The sub-agent touches `heartbeat` at least every 60 seconds. The `mtime` of `heartbeat` is the freshness indicator.

A sub-agent that's about to spend longer than 60 seconds in a single tool call (e.g., a long `nmap` scan) wraps that call so a background thread keeps the heartbeat fresh.

### 2.3 Clean exit

On successful completion the sub-agent:

1. Writes `result.json` with the structured result (see §3).
2. Writes `.done` containing `finished_at`, `result_summary`, `artifact_paths` (relative to engagement root).
3. Deletes `.running`.
4. Returns control to the orchestrator (Agent-tool path) or just exits (filesystem-coordinated path).

### 2.4 Crash detection

The orchestrator runs a reaper check on every operating-loop iteration. For each dispatch directory under `engagements/<id>/`:

- If `.done` exists → dispatch is complete; orchestrator reads `result.json`.
- If `.crashed` exists → dispatch already declared dead; orchestrator reads it.
- If `.running` exists and `heartbeat` mtime is **older than `2 × expected_max_duration_seconds`** (or older than 300 seconds if `expected_max_duration_seconds` is unset), the reaper:
  1. Writes `.crashed` with `crashed_at`, `crash_reason: heartbeat-stale`, `last_heartbeat_age_seconds`, and a pointer to whatever partial artifacts exist.
  2. Deletes `.running`.
  3. Appends a `kind: phase-crash` line to `logs/audit.jsonl`.

### 2.5 Orchestrator-side handling

Per `.done` or `.crashed`, the orchestrator applies the policy table in §4.

## 3. `result.json` schema (clean exit)

```json
{
  "dispatch_id": "01JEXAMPLE...",
  "agent": "exploit-agent",
  "phase": "verification",
  "status": "ok" | "ok-with-warnings" | "partial",
  "started_at": "2026-05-15T18:00:00Z",
  "finished_at": "2026-05-15T19:42:00Z",
  "artifact_paths": [
    "findings/F-007.md",
    "evidence/F-007/request.http",
    "evidence/F-007/response.http"
  ],
  "summary": "1 finding confirmed (F-007, medium); 3 candidates parked as unverified",
  "warnings": [],
  "needs_operator": null,
  "next_recommended_phase": "reporting"
}
```

`status: partial` means the agent ran out of time, hit attempt cap, or chose to stop early but the artifacts produced so far are internally consistent and usable. Distinct from `.crashed`.

`needs_operator: <message>` is how a sub-agent escalates without a crash. The orchestrator relays the message to Discord and pauses the phase until the operator answers.

---

## 4. Orchestrator policy by outcome

| Flag | `result.json` status | Orchestrator action |
|---|---|---|
| `.done` | `ok` | Accept artifacts. Update `state.json`. Move to next phase. |
| `.done` | `ok-with-warnings` | Accept artifacts. Log warnings. Notify operator via Discord if any warning has `severity: high`. Move on. |
| `.done` | `partial` | Accept artifacts. Append a `phase-partial` audit line. Ask operator (Discord) whether to retry the phase, accept partial, or end engagement. |
| `.crashed` | n/a (no `result.json` or unreadable) | Mark phase `crashed`. Read whatever partial artifacts the agent wrote — apply §5 usability rules. Notify operator. Wait for operator instruction (retry / skip / end). |
| `.crashed` | `result.json` exists but incomplete | Same as above, but use `result.json` as a hint to which artifacts the agent claims are usable. Cross-check against §5. |

The orchestrator **never** silently retries a crashed sub-agent. Every retry requires explicit operator approval, even within signed scope.

---

## 5. Partial-artifact usability rules

When a sub-agent crashes, some files on disk may be half-written or corrupted. The orchestrator applies these per-artifact rules:

| Artifact | Usability after crash |
|---|---|
| `logs/audit.jsonl` (engagement-level) | Always usable up to the last line whose `this_hash` verifies. Truncate logically at the first verification failure. |
| `findings/<F-NNN>.md` | Usable if YAML frontmatter parses AND `status: confirmed` AND all `evidence:` paths exist. Otherwise demote to `findings/candidates.jsonl` entry and mark `from-crashed-run`. |
| `evidence/<F-NNN>/*` | Usable if the file's size matches the size recorded in the corresponding `audit.jsonl` `evidence-write` line. Mismatch → quarantine, do not include in reports. |
| `recon/asset-graph.json` | Usable if JSON parses and the schema validator passes. Otherwise dispatch a fresh `recon-agent` to rebuild. |
| `enum/surface-map.json` | Same rule as asset-graph. |
| `findings/candidates.jsonl` | Each line independent — usable lines retained, malformed lines moved to `findings/candidates.malformed.jsonl` for operator triage. |
| `report/*.{md,docx,pdf}` | Never used post-crash. Reporting always re-runs in full. |

---

## 6. Retry semantics

When the operator approves a retry of a crashed phase, the orchestrator:

1. Renames the prior dispatch directory to `<phase>/.dispatch/<dispatch-id>.crashed/`. Nothing is deleted.
2. Creates a new dispatch directory with a fresh ULID.
3. Hands the new dispatch a `task.json` that includes a `prior_dispatch_ref` pointer so the sub-agent can read the partial work and resume rather than restart from zero.
4. Appends a `kind: phase-retry` audit line that references both dispatch IDs.

The sub-agent is responsible for deciding which partial artifacts to trust on resume — it does so by the §5 rules.

---

## 7. What this doc does NOT cover

- In-process agent panic handling — that's the sub-agent's own responsibility (catch exceptions, mark `status: partial`, write `result.json`, exit cleanly).
- Out-of-memory kill recovery (no `.crashed` written because the agent didn't get a chance) — handled by the reaper's heartbeat timeout in §2.4.
- The full Claude Code `Agent`-tool integration — separate skill spec, lives under `/skills/sub-agent-dispatch/SKILLS.md` when implemented.
